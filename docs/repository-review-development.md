# Multi-ecosystem repository review

Status: unreleased feature branch. Validation date: 2026-11-27 (Asia/Seoul).

## Implemented scope

`repo-plan` discovers recognized dependency files without network access. `repo-collect` screens Yarn Berry/Cargo/Gradle locks, Maven resolved trees, Swift pins, Go declarations and imported container image reports, preserving project occurrences and available dependency relationships. Identities and deduplication include the ecosystem. Go declarations are never called a selected build list. `repo-render` verifies sealed evidence and regenerates Korean/English Markdown and offline HTML. MCP exposes the same planning and collection functions; the CLI-only plugin is generated from canonical source.

The initial adapter uses a bounded PyYAML 6.0.3 string-only loader instead of adding an external scanner executable. Public metadata comes from the existing deps.dev and OSV clients. No new outbound service is introduced. Networked repository collection requires confirmed public identifiers or an explicit identifier allowlist and retains existing service, identifier, TLS and additional-review policies. OSV single-query pagination now checks identifiers as batch requests already did.

The new snapshot and verdict schemas are `oss-gate.repository-review/1` and `oss-gate.repository-policy/1`. The verdict covers identified dependency vulnerabilities and licenses, distinguishing locked, resolved and declared versions. It does not assert source-code, maintenance, deployment or root-project-license coverage. It is separate from package policy/3 and existing portfolio/reassessment commands. Unknown licenses retain the existing conservative license classifier; additional restrictions and attributed license decisions remain attached to their exact evidence.

## Input and resource boundaries

- Local directory only; no automatic clone, install, build or execution of target code.
- Berry lock format metadata versions 4 through 10. Workspace manifests, ordinary npm descriptors and npm aliases are supported. Non-npm sources, patches, installed peer bindings and unresolved mappings remain gaps.
- Workspace glob support: segment-local `*`, `?`, character classes and recursive `**`. Negations and brace expansion are not implemented and remain gaps.
- Generated directories (`.git`, `node_modules`, `.yarn`, `.venv`, `venv`, `target`, `build`, `dist`, `.gradle`, `.build`, `Pods`) and the selected output directory are excluded and recorded. Symlinks are not followed. `.gitignore` is not interpreted.
- Discovery bounds: 50,000 directory entries, 2,000 recognized files, 8 MB per file and 32 MB total input. Lock parsing bounds: 10,000 entries, 250,000 YAML nodes, depth 16, 256 workspaces and 100,000 cumulative workspace graph visits. Limits produce gaps rather than approval.
- Query cap: 2,000 unique versions by default, configurable to 1..10000. Eight metadata/detail workers. Advisory details: 1,000. OSV pagination: at most 20 processed pages per query and 200 follow-up requests per run. Failed, malformed or incomplete responses remain unknown.
- The online inventory includes every supported locked/resolved package identity and Go requirement, including development/optional entries and unattributed entries. Coverage denominators count identified ecosystem/name/version tuples, not unresolved components or unsupported ecosystems. The scanner does not claim build-specific reachability.
- Input bytes are represented by path, size and SHA-256. Unsupported source locators are represented by a sanitized package/protocol and locator hash; credential-bearing URLs are not copied into reports.

## Go and Cargo implementation and validation

- `core/gomod.py` reads single/block directives, quoted tokens, direct/indirect requirements, exclusions, exact module replacements and `go.work` members/overrides. Conflicting, unreadable or incomplete workspace replacement contexts suppress uncertain identities. Local replacement paths are hashed, not sent as original modules. Checksum files contribute hashes only. Every Go project adds `go_build_list_unverified`: declaration versions do not prove minimal-version selection or a complete graph. No Go command is executed.
- `core/cargo.py` uses pinned Tomli 2.5.0 (MIT) on all supported Python versions. It accepts lock formats 3/4, distinguishes crates.io from Git/alternate registries/local entries, follows locked edges and maps workspace aliases, inherited dependency/version fields, path members and target/build/dev groups. Common Cargo caret/tilde/wildcard/exact/comparison requirements are checked; prerelease or unsupported syntax remains a gap. Invalid dependency tables are never interpreted as wildcard requirements. Unknown source/configuration/replacement behavior stays unverified. External package-manager configuration and feature-selected deployment reachability are outside scope.
- Cargo bounds: 10,000 lock packages, 250,000 TOML tree nodes, depth 32, 256 workspace/path manifests and 100,000 cumulative graph visits. Go files are limited to 20,000 lines, in addition to common file/discovery limits. Local path references only resolve inventory keys; they never cause arbitrary file reads or execution.
- Full suite: 151 tests on Python 3.13.5 and 3.10.18, including 17 Go/Cargo regressions. Mixed tests distinguish same-name npm/crates.io packages, preserve blocked private Go names and exercise source URLs, replacement conflicts, workspace misses, checksum history, stale lock edges, unsupported ranges, malformed TOML and translated report gaps.
- Refreshed runtime/development audits found no known vulnerabilities. The Python 3.10 license inventory contains 35 runtime distributions, including Tomli's MIT metadata. New parsing does not add outbound services; collection still uses deps.dev and OSV under existing identifier/service/TLS policy.
- Parsed `BurntSushi/ripgrep` commit `3e85c6c148fdce38a99ceeb9d2780dc7b03b4a4f`: 11 Cargo projects and 73 crates.io lock occurrences. The separate fuzz workspace's outside-workspace local path remains unverified. Parsed `gin-gonic/gin` commit `0f09c3a9b4626d9fe9979cf4d0521d6ae32ab646`: one Go project and 32 declared module requirements, retaining the Go build-list gap. These are parser checks, not adoption verdicts for the upstream projects. Exact input hashes are retained in ignored `verification-local/repository-review/stage2/upstream/validation.json`.
- A live synthetic mixed-repository fixture queried public `npm:is-number@7.0.0`, `cargo:itoa@1.0.15` and `go:golang.org/x/text@v0.22.0`. All three OSV and license lookups completed; the saved run contains two advisory groups affecting one version, plus the Go build-list gap, and is conditional. Counts describe the saved run only. Evidence/report paths are in ignored `verification-local/repository-review/stage2/live-result.json`. Korean/English reports, declared/locked labels and language navigation were visually checked in Aside.
- Ruff, generated CLI parity, eight-tool MCP smoke, examples, site and distribution checks passed. The isolated candidate archive was checked separately; release versions remain unchanged; publishing a release is separate from this development stage.

## Java/Kotlin, Swift and container implementation

- `core/jvm.py` reads Maven Dependency Plugin JSON trees (`dependency-tree.json`) and modern/buildscript/legacy Gradle dependency locks. Java and Kotlin both use Maven coordinates. Maven direct/transitive edges, scopes and variants are retained; omitted verbose nodes are excluded, including their subtrees. Gradle configurations and multiple locks remain associated with one project. Dynamic/SNAPSHOT dependencies, system paths, variants, unresolved POM identities and build/repository/profile freshness retain gaps. Target build tools and executable manifests are never run.
- `core/swift.py` accepts Package.resolved schemas 1/2/3 and nested Xcode locations. Versioned HTTPS Git pins become OSV SwiftURL host/path identities without scheme or `.git`; source revisions remain occurrence evidence. Registry/local/branch-only pins, mirrors, manifest freshness and noncanonical advisory aliases remain gaps. No Swift deps.dev metadata request is made. Unknown Swift licenses retain the existing hold classification.
- `core/containers.py` parses Dockerfile stages and Compose image declarations, then imports native Trivy schema 2 container-image and Grype image reports. Exact normalized repository plus manifest SHA-256 identifies a declaration/report match. Tags, image config IDs and Trivy ArtifactID are not substitutes for a manifest digest. No scanner, image pull, registry request or target build executes.
- Container decisions retain suppressed/ignored findings, distinguish package/version/namespace/advisory tuples, and hold high/critical severity or numeric CVSS >= 7. Unknown severity and zero imported findings cannot establish allow. Component licenses receive existing restrictions/additional policies. Attributed license finding hashes bind both image identity and imported file hash. Reports distinguish license/additional-policy component results from imported vulnerability results.
- Native image environment, scanner configuration and freeform descriptions are omitted from normalized evidence. Source SHA-256 is sealed, but raw scanner JSON is not copied. Original reports must be retained independently when required. Input filtering, database/scanner freshness, complete component/license coverage and final build contents remain unverified. Container counts are separate from online query denominators.
- Shared JSON parsing rejects duplicate keys, nonfinite values, non-object roots, more than 250,000 tree nodes or depth 64. JVM and Swift limits are 10,000 nodes/pins; container list and aggregate import limits are 20,000 records, in addition to common discovery/file bounds. XML declarations/entities and Compose aliases/tags are rejected. No new runtime dependency or outbound host was added.

## Remaining scope

An explicitly supplied Go selected-build-list or standardized SBOM import is a future extension. Swift license acquisition and advisory aliases need evidence-backed source adapters. General dependency resolution, build execution, reachability and final image generation are outside this implementation. Docker Scout is a separate service, not an assumed public Docker Hub vulnerability database. Repository review remains unreleased on this feature branch; package review and portfolio schemas remain unchanged.
