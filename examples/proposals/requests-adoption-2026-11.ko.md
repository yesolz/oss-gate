# Requests 도입 제안서

근거 기준일: 2026-11-17 · 제안 예제 · 검증: **WARN**

> 과거 Requests 2.34.2 스냅샷에 근거한 제안서 예제다. 실제 팀의 승인, 운영 환경, 법무 회신 또는 현재 보안 상태를 확인한 문서가 아니다.

## 1. 배경과 대상

외부 HTTP API를 호출하는 Python 서비스에 Requests를 사용하는 상황을 가정한다. “백엔드 API 팀”은 제안을 설명하기 위한 가정이며 실제 조직의 요구사항을 확인한 것은 아니다. Requests 2.34.2는 정책 v2에서 조건부다. 남은 도입 질문은 certifi@2026.10.23의 MPL-2.0 의무와 실제 수정·배포 방식이다. [근거 1, 2]

패키지 자신의 라이선스는 Apache-2.0이다. 저장된 직접 의존성은 certifi, charset-normalizer, idna, urllib3 네 개이며 간접 의존성은 없다. 이 그래프가 특정 서비스의 실제 설치 환경과 같은지는 확인하지 않았다. [근거 2]

## 2. 제안하는 도입 조건

**환경 확인.** 실제 런타임과 lockfile을 검토한다. 과거 스냅샷의 버전은 Requests 2.34.2, certifi 2026.10.23, charset-normalizer 3.5.2, idna 3.20.0, urllib3 2.8.0이다. 이 목록은 비교 기준이며 현재 시점의 설치 권고가 아니다. 다른 버전이나 extras를 사용할 경우 해당 환경을 새로 검토한다. [근거 2, 3]

**라이선스 결정.** certifi 파일 수정, CA 번들 재배포, 실제 배포 산출물을 확인한 뒤 MPL-2.0 의무에 관한 사람의 결정을 기록한다. 이 제안은 해당 결정을 운영 도입의 선행 조건으로 두는 방안이다. 법무 회신이 이미 있거나 완료됐다고 가정하지 않는다. [근거 1, 2]

**운영 설정.** TLS 검증을 유지하고, 프록시·CA 설정·`.netrc`·`trust_env`가 배포 환경에서 어떻게 적용되는지 확인한다. 클라이언트 키는 별도 비밀 관리와 파일 권한 검토가 필요하다. 이는 과거 위키 설명에서 도출한 검토 항목이며 실행 검증된 운영 설정은 아니다. [근거 3]

**선택 기능.** PySocks·chardet 등이 추가되는 extras를 켜기 전에 의존성 범위를 다시 확인한다. 버전 변경, extras 변경, 새로운 권고 또는 배포 방식 변경은 재검토의 계기로 삼는다. [근거 3]

## 3. 기대 효과와 측정

| 지표 | 저장 자료의 기준값 | 제안하는 목표 | 확인 방법 |
|---|---|---|---|
| 알려진 권고 | Requests와 조회된 네 의존성에서 0건 | 결정 시점의 새 검토에서 미해결 높은 심각도 항목 없음 | 새 스냅샷과 실제 lockfile 대조 |
| certifi 라이선스 결정 | 기록 없음 | 운영 도입 전 사람의 결정 기록 | 검토 기록 또는 티켓 |
| 실제 환경의 TLS 검증 비활성화 | 미측정 | 승인되지 않은 비활성화 0건 | 코드·설정 검토 |
| 검토하지 않은 추가 의존성 | 미측정 | 변경 시 재검토 | lockfile diff와 검토 자료 대조 |

목표는 제안이며 달성 결과가 아니다. 책임자, 예산, 일정과 대안 비교는 아직 정하지 않았다. 후보 대안을 조사하지 않았으므로 Requests가 모든 대안보다 우수하다고 주장하지 않는다.

## 4. 위험과 한계

Scorecard는 8.2이지만 2026-08-24의 자료다. Branch-Protection은 미평가(-1), Vulnerabilities 체크는 누락이다. 과거 에이전트 검토는 WARN이며 리다이렉트 인증 헤더 등 일부 위키 주장이 재현되지 않았다. 위키는 버전에 고정돼 있지 않다. [근거 1, 2, 3]

정기 리포트의 Flask 원본은 저장소에 없어 집계에서 제외했다. 따라서 옛 문서의 전체 포트폴리오 결과를 이 제안의 검증 근거로 사용하지 않는다. [근거 4]
